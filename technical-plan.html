Three findings that reorder the build

Read before planning sprints. Each of these moves a task from "later" to "first", and one of them is a live data bug.

Finding 1 · There is no geometry. Anywhere. Routing resolves a GPS pin → jurisdiction → department → officer by point-in-polygon. The repo contains zero boundary data — verified across all of data/, schema/ and scrapers/: no polygons, no GeoJSON, not one lat/lng in any data file.

This is easy to miss because the artifacts look geo-ready: ticket.schema.json has lat/lng, and LGD covers 4,814 ULBs nationally. But LGD is codes and names only. There is nothing to test a point against. Worse, no ward layer exists at any level — LGD stops at local body, while a ward is the unit an officer actually owns (BBMP alone has 198).

Consequence: boundary acquisition (D1) is the single upstream blocker. Routing, officer assignment, SLA, the feed's distance filter and clustering's candidate radius all depend on it. It is task one, not a later data chore.
Finding 2 · Jurisdiction coverage is national; reachable officers number ~380 4,814 ULBs with 99.9% district matching, against 92 central + 88 appellate + 37 state + 163 district contacts — and the district contacts cover 7 states / 11 districts, with only 68 of 163 rows carrying a department label. This is exactly why PRD §12's three routing tiers exist. Most of India is Tier 3 on day one. Build the tiering before the officer queue, or the queue will be empty and the UI will lie about it.
Finding 3 · state_agencies.csv is column-shifted — a live bug Unquoted commas inside water_authority_name shift every later field one column right for KARNATAKA and TELANGANA — the two states a Bengaluru or Hyderabad demo needs most. 
KARNATAKA, parsed by csv.DictReader:
  water_authority_name  = 'Bangalore Water Supply and Sewerage Board (BWSSB'
  water_authority_scope = ' Bengaluru only) / Karnataka Urban Water Supply…'
  discom_names          = 'mixed'                     ← should be BESCOM;MESCOM;…
  verified              = 'Karnataka Fire and Emergency Services'   ← should be FALSE
Any code reading discom_names gets the literal string "mixed". Fix by quoting those two rows before D3. Also note 0 of 36 rows are verified, so water and electricity must not auto-route at all until verification completes.

Fallback ladder when a pin hits no polygon 1. ST_Contains at the most specific level available  →  2. nearest district centroid within 25 km  →  3. reverse-geocode to a district name, fuzzy-match the LGD name table  →  4. routing_tier = 'UNMAPPED', a valid outcome rather than an error.

Why one Next app, not three

All three surfaces share the issue type, the status pills, the Supabase client and the query layer. Three deployables means three copies of the design system and a versioning problem between them. Route groups give clean URL separation with none of that cost.

Why a separate worker

Clustering, ASR and verification exceed Edge Function timeouts. The worker polls pgmq and runs anywhere (Railway, Fly, a VM). Edge Functions stay for sub-second work only — enqueue and notify.

Why packages/shared

Scoring and enums are imported by both the app and the workers. Duplicating the status enum across two runtimes is how they silently drift. scoring.ts is pure and unit-tested — no DB, no network.

Authentication & authorization B1 B2

Google OAuth for everyone. No SMS provider needed, and — unexpectedly — it makes officer onboarding better than the phone design it replaces.

Why Google is an upgrade for officers, not a compromise Officer onboarding was blocked on an open question: do government rosters carry personal mobile numbers? Mostly they don't. But they carry email — 100% of the 92 central, 88 appellate and 37 state rows, and 66% of district rows. Matching a Google sign-in against a roster by email is a direct join on data we already hold, and a @gov.in / @nic.in domain is an affiliation signal a phone number never was. This closes PRD §23's roster question.
What it costs on the citizen side — plan for it Phone OTP was the anti-spam anchor: Indian SIMs are KYC'd, so one number meant one traceable person. Google accounts are free and unlimited, so that property is gone. Compensate with: rate limits keyed on user id and IP, a minimum account age before high-trust actions, one report per issue per user per 24h, device fingerprinting for burst detection, and holding the crowd counter for review on abnormal spikes. Do not skip this — the report count drives priority, so it will be gamed.

Provisioning rules

  • Everyone starts as CITIZEN. There is no "sign up as officer" path.
  • Roster email match is the strong signal → offer the claim immediately, pre-filled from the roster row.
  • Gov domain but no roster row → weaker. Allow a claim request, but it needs admin approval; do not auto-provision on domain alone.
  • Confirmation is always explicit. A wrong match must never silently hand someone authority. The user taps to accept.
  • One-to-one only. If an email matches multiple roster rows, provision nothing and route to manual review.
  • Every grant is logged with roster record, source file and match method.

JWT claims — why RLS needs them

Without claims, every RLS policy runs a subquery against government_officers on every row of every query. Put role and scope in the token instead.

-- Supabase custom access token hook
create or replace function public.custom_access_token(event jsonb)
returns jsonb language plpgsql as $$
declare claims jsonb; u record;
begin
  select r.role, o.department_id, o.jurisdiction_id,
         o.jurisdiction_level
    into u
  from public.users r
  left join public.government_officers o
    on o.user_id = r.id and o.is_active
  where r.id = (event->>'user_id')::uuid;

  claims := event->'claims';
  claims := jsonb_set(claims,'{app_role}', to_jsonb(coalesce(u.role,'CITIZEN')));
  claims := jsonb_set(claims,'{dept_id}',  to_jsonb(u.department_id));
  claims := jsonb_set(claims,'{juris_id}', to_jsonb(u.jurisdiction_id));
  claims := jsonb_set(claims,'{juris_lvl}',to_jsonb(u.jurisdiction_level));
  return jsonb_set(event,'{claims}',claims);
end $$;

create or replace function auth.app_role() returns text
language sql stable as $$
  select coalesce(current_setting('request.jwt.claims',true)::jsonb->>'app_role','ANON')
$$;
create or replace function auth.juris_id() returns bigint
language sql stable as $$

-- public feed: PUBLIC, published, not held
create policy issues_public_read on issues for select
using (visibility='PUBLIC' and published_at is not null and status <> 'HELD');

create policy issues_gov_read on issues for select
using (auth.app_role() = 'GOVERNMENT' and jurisdiction_id = auth.juris_id());

-- supervisors: whole subtree, via the jurisdiction closure
create policy issues_supervisor_read on issues for select
using (auth.app_role() = 'GOVERNMENT'
   and jurisdiction_id in (select id from jurisdiction_descendants(auth.juris_id())));
Claims go stale — handle it A JWT minted before a role change still carries the old claims until it refreshes. On any officer provisioning, deactivation or jurisdiction change, force a session refresh and keep a server-side check on write paths. Read paths can tolerate up to one token lifetime of lag; writes cannot.

Route guards

middleware.ts refreshes the session and gates /gov and /admin on app_role. This is UX, not security — RLS is the real boundary. A guard that fails open must still leak nothing.

Anonymous reading

The feed and issue pages render server-side for logged-out users via the anon key, which sees only the public policy. Actions prompt sign-in and resume the exact intent afterwards.

Migration path back to phone

Keep users.phone nullable from day one and treat identity as a set of linked providers. Adding phone OTP later becomes an additional factor for a higher trust tier, not a rewrite.

Resolution chain B3 B4

The agent tags a category. SQL finds the authority. No model participates in deciding who owns an issue.

create or replace function resolve_authority(
  p_lat double precision, p_lng double precision, p_category text
) returns table (jurisdiction_id bigint, authority_id bigint,
                 routing_tier text, match_method text)
language plpgsql as $$
declare v_jur bigint; v_method text;
begin
  -- 1. most specific containing polygon
  select id into v_jur from jurisdictions
  where ST_Contains(geometry, ST_SetSRID(ST_Point(p_lng, p_lat), 4326))
  order by case level when 'WARD' then 1 when 'ZONE' then 2
                      when 'ULB' then 3 when 'DISTRICT' then 4 else 5 end
  limit 1;
  v_method := 'POLYGON';

  -- 2. fallback: nearest district centroid within 25 km
  if v_jur is null then
    select id into v_jur from jurisdictions
    where level = 'DISTRICT'
      and ST_DWithin(centroid::geography,
            ST_SetSRID(ST_Point(p_lng,p_lat),4326)::geography, 25000)
    order by centroid <-> ST_SetSRID(ST_Point(p_lng,p_lat),4326)
    limit 1;
    v_method := 'CENTROID_FALLBACK';
  end if;

  -- 3. walk taxonomy resolution_order, first match wins
  return query
  select v_jur, a.id,
    case
      when exists (select 1 from government_officers o
                   where o.jurisdiction_id = v_jur and o.is_active)
        then 'ONBOARDED'
      when a.grievance_email is not null
       and a.verification_status = 'VERIFIED' then 'CONTACTABLE'
      else 'UNMAPPED'
    end,
    coalesce(v_method,'NONE')
  from category_authority_rules r
  left join authorities a
    on a.authority_type = r.authority_type
   and a.jurisdiction_id = v_jur
  where r.category_id = p_category
  order by r.seq
  limit 1;
end $$;
No officer found is a valid result It sets routing_tier = 'UNMAPPED' and the UI says so honestly — "Published · no authority contact yet". Never a fabricated assignee, never a fake SLA countdown against a department that has not heard of Swaram.

C3 Safety gate

Five verdicts: clear / redact / hold / emergency / reject. The issue is always created, classified, routed and given an SLA; only publication is gated. published_at stays null while HELD. Fails open for the department, closed for the feed.

select i.id, i.public_id,
       ST_Distance(i.location, $1::geography) as metres,
       1 - (r.embedding <=> $2) as text_sim
from issues i join reports r on r.issue_id = i.id
where i.category_id = $3
  and i.status not in ('CLOSED','MERGED')
  and ST_DWithin(i.location, $1::geography, $4)
order by text_sim desc
limit 10;

SQL narrows candidates cheaply; the agent then judges location + image + description together. Merge policy: ≥0.90 auto · 0.75–0.90 officer confirms · <0.75 nothing. Older issue survives and keeps its public_id; the younger redirects.

create or replace function gov_kpis(p_juris bigint, p_dept bigint)

11.2 Admin dashboard H1 — /admin

All four panels read from materialized views refreshed on a cron. Computing department performance live across a national table on every page load will not survive the first real dataset.

-- Department performance (PRD §11 + §21)
create materialized view mv_department_performance as
select d.id, d.name,
  count(*)                                              as total,
  count(*) filter (where i.status in ('RESOLVED','CLOSED')) as resolved,
  round(100.0 * count(*) filter (where i.status in ('RESOLVED','CLOSED'))
        / nullif(count(*),0), 1)                        as resolution_rate,
  percentile_cont(0.5) within group (
    order by extract(epoch from (i.acknowledged_at - i.created_at))/3600
  )                                                     as median_ack_hours,
  percentile_cont(0.5) within group (
    order by extract(epoch from (i.resolved_at - i.created_at))/86400
  )                                                     as median_resolve_days,
  round(100.0 * count(*) filter (
        where i.resolved_at is not null and i.sla_due_at >= i.resolved_at)
        / nullif(count(*) filter (where i.resolved_at is not null),0),1)
                                                        as sla_compliance,
  round(avg(i.satisfaction_score) filter (
        where i.satisfaction_score is not null),1)       as avg_satisfaction,
  count(*) filter (where i.status = 'REOPENED')          as reopened
from departments d
left join issues i on i.department_id = d.id
group by d.id, d.name;

create unique index on mv_department_performance (id);

-- AI quality (PRD §11) — measured against human overrides, not self-reported
create materialized view mv_agent_quality as
select agent_name,
  count(*)                                                as runs,
  round(avg(confidence)::numeric, 3)                      as avg_confidence,
  round(100.0 * count(*) filter (where was_overridden)
        / nullif(count(*),0), 1)                          as override_rate,
  round(avg(latency_ms))                                  as avg_latency_ms,
  date_trunc('day', created_at)                           as day
from agent_runs
group by agent_name, date_trunc('day', created_at);

-- Coverage: the §12 tier picture, which is the growth constraint
create materialized view mv_coverage as
select j.id, j.name, j.level,
  count(i.*)                                                    as issues,
  count(*) filter (where i.routing_tier = 'ONBOARDED')          as tier1,
  count(*) filter (where i.routing_tier = 'CONTACTABLE')        as tier2,
  count(*) filter (where i.routing_tier = 'UNMAPPED')           as tier3
from jurisdictions j left join issues i on i.jurisdiction_id = j.id
group by j.id, j.name, j.level;

select cron.schedule('refresh-dash','*/15 * * * *', $$
  refresh materialized view concurrently mv_department_performance;
  refresh materialized view concurrently mv_agent_quality;
  refresh materialized view concurrently mv_coverage;
$$);

Overview

Volume, open/in-progress/resolved/overdue, and the created-vs-resolved crossover — the single clearest health signal. Trend over 7/30/90 days.

Departments

From mv_department_performance, ranked, with movement vs last period. Sorted by satisfaction, not closure count — closing fast at 30% satisfaction must look worse than closing slowly at 90%.

Coverage map

From mv_coverage. Choropleth by tier — where officers are onboarded vs where issues pile up unheard. This is the business dashboard, not just an ops one.

AI quality

From mv_agent_quality. Override rate per agent over time is the honest measure; confidence is only a signal. A rising override rate is a regression alarm.

11.3 Public statistics — the accountability output

  • Per-ward public page at /stats/[jurisdiction], server-rendered and indexable, reading the same materialized views.
  • Publishes resolution rate, median time and satisfaction — the PRD treats department performance as publishable, so this is a feature, not a leak.
  • Also publishes moderation volume — items removed per period, per §20's transparency rule.
  • Feeds H3: the weekly newspaper and the national map are views over this same data, not a separate pipeline.
Two rules for every dashboard number 1 · Never mix issue count with report count. "27 people affected" is reports; "how many problems exist" is issues. Conflating them destroys both numbers and it is the easiest mistake to make in a GROUP BY.

2 · Tier-2 and Tier-3 issues have no SLA. Exclude them from SLA compliance rather than counting them as breaches — a department that never onboarded cannot breach a promise it never made, and counting it that way makes the metric meaningless.
